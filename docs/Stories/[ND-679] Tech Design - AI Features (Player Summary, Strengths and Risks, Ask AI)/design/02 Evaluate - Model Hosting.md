## Recommendation

**Recommended option: Option D — In-house adapter interface.**

Option D is the cheapest option that still mitigates the provider lock-in risk every sibling decision (1, 2, 3) flagged as outstanding. Swapping providers later means writing one new adapter implementation, not changing every call site across BFF, Synthetic Layer, and agent code, per the Requirements matrix's "low cost of switching provider later" row. It adds no new Azure resource and no new network hop beyond the one egress rule Option A already requires, so it carries none of Option C's added operational surface.

Option C centralizes guardrails more completely, but Research's own assessment calls it "the most moving parts of any option... for a decision that otherwise has none of the three features' functional complexity." That cost is disproportionate at this platform's scale (10-30 users) unless the Frame's proposed Cost guardrail and Observability ECs are confirmed as strict requirements, which they are not yet (see Open Questions). Option B is excluded until the NUFC/Michael provider sync lands, since its viability depends entirely on the eventual provider having a first-party Azure equivalent. Options E and F are both excluded from this decision's recommendation on the same ground: each fails the criterion of working independently of the other cross-cutting decisions, so adopting either here would resolve multiple decisions by platform lock-in rather than by an informed, separate choice for each. Foundry Prompt Agents (E) additionally pre-empts Decision 6 outright, since its thread/run engine leaves no framework seam for Decision 6 to resolve. Foundry Hosted Agents (F) is disqualified outright by this platform's TypeScript/Node.js stack requirement, since it supports only Python and C#.

**Falsifiability.** If Solution confirms the Cost guardrail and Observability ECs as non-negotiable requirements, Option C's centralization advantage becomes materially more valuable and this recommendation should be revisited. Reaching equivalent centralization under Option D would require shipping the adapter as a shared internal library across every layer that calls it, per Decision 5's outcome: a real but smaller cost than standing up Option C's gateway service.

**Carried risk into Solution.** Decision 2's Evaluate identified that its recommended option's per-player pre-computed half runs at full player-universe scale (130,000 platform assumption; ~47,767 actual via `players_search_index`) — tens of thousands of LLM calls in a single nightly batch, not the handful of ad-hoc calls Decision 4's options were originally compared against. Option D's "low engineering/build cost" and "no new resource" scores above assume a thin pass-through adapter; sustaining that batch volume against a yet-unselected provider's rate/token quota without dropped or throttled calls requires the adapter to own its own backpressure, retry, and rate-limiting logic, the same capability Option C would get for free from a gateway resource. This does not change the recommendation (Option D's adapter can absorb this as additional build scope, and Option C's disproportionate operational surface argument still holds), but it is real, uncosted scope that Solution must account for, not a hypothetical centralization nicety.

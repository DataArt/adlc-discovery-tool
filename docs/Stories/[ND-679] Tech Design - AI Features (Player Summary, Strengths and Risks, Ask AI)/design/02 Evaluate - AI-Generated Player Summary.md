# ND-679: AI-Generated Player Summary — Evaluate

_Produced by the Evaluate phase._

## Context

Decision 5 (Agent Runtime Hosting) recommends Option B: a new sibling Azure Container App, hosted as one new, shared deployment unit reused across Decisions 1, 2, and 3's generation needs. Decision 6 (Agent Orchestration Framework) recommends Option A: LangGraph (TypeScript), since Container Apps' persistent process is exactly the hosting shape LangGraph's checkpointer assumes. Option F below (the LangGraph-on-Container-Apps agent option from `01 Research - AI-Generated Player Summary.md`) is consistent with both Decisions 5 and 6. Option F's weakness is unrelated to hosting or framework: its own Research already questioned whether its dynamic "decide what to fetch" capability adds value when this feature's inputs are fully known and bounded ahead of time, since Player Summary needs a fixed, known set of profile/metrics/rankings data, not open-ended tool selection.

## Recommendation

**Recommended option: Option E's shape, with one revision to its Research.** The generation and cache-miss handling live in dedicated compute; the BFF stays a pure reader. The revision: host that compute on Decision 5's shared Container App deployment, not a brand-new Synthetic Layer HTTP trigger class.

Option E already scores best on the two requirements that matter most once Decisions 4, 5, and 6 are in place: keeping the BFF thin, and giving Ask Magpie's sub-agent (Decision 3) a single source of truth to read. Its one weakness in the original Research, needing a genuinely new Synthetic Layer HTTP trigger class that doesn't exist in code today, is resolved by Decision 5's own outcome: a new Container App deployment is already being stood up to host Ask Magpie's orchestrator. Player Summary's cache-miss generation (assemble data from PostgreSQL, call the model, write the cache) is a short, bounded piece of work that fits inside that same shared deployment rather than requiring a second, separate trigger class. This converges Decisions 1, 2, and 3 onto one shared generation compute unit.

**Option F is not recommended.** Its framework and hosting assumptions are consistent with Decision 5 (Container App) and Decision 6 (LangGraph), but a proportionality problem remains, independent of hosting: Player Summary's inputs are fully known and bounded ahead of time (profile, metrics, rankings, milestones — a fixed, enumerable set), so an agent's dynamic "decide what to fetch" capability is solving a problem this feature does not have. A deterministic cache-aside shape (Option E) assembles the same data with no tool-selection overhead, no multi-step latency, and a materially simpler mid-run authorization story for the medical/scouting role-restriction gap this design still needs to close. Option F is the right shape for Ask Magpie (Decision 3), where genuine multi-capability routing exists, but not for Player Summary's single, fixed generation task.

Option D remains a reasonable fallback. If Solution finds that keeping model-calling inside the BFF is simpler to build than wiring a cross-deployment call into the shared Container App unit, revisit toward D. That cost/complexity tradeoff is a real implementation-time question, not one architecture alone can settle.

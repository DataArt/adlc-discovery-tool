## Recommendation

**Recommend Option C's shape (per-employee pre-computed signals/narrative + runtime comparison-weave), hosted on Decision 5's shared Container App deployment for both halves.**

Why: Option C already scores best on the core tension this decision exists to resolve: genuine comparison-aware prose without Option B's combinatorial cost blowup. Its one structural gap (the comparison-weave half needs a request-driven trigger that the not-yet-built Synthetic Layer doesn't have today) is resolved the same way as Decision 1's recommendation: route both the nightly per-employee batch and the on-demand comparison-weave call through Decision 5's shared Container App deployment, rather than inventing a new Synthetic Layer trigger class. This also means Decisions 1, 2, and 3 now share one architecturally consistent AI generation compute unit, directly supporting the converged picture the Solution phase should document.

Option A alone is rejected only because it can't produce genuine comparison narrative quality; Option B is rejected on cost-boundedness grounds (high-cardinality comparison sets make its cache-hit assumption unreliable, and it fails the BFF's documented bounded-exception pattern as currently scoped). Option D is a reasonable minimal fallback for a First Release MVP if Solution finds C's two-generation-path complexity too much to build in the available time, but does not fill the ADLC-105 Profile gap as cleanly. **Option E is rejected on proportionality grounds.** It is infrastructure-consistent with Decisions 5 and 6 (Container App, LangGraph), but the hard part of this task (signal derivation) is already deterministic and settled, so a dynamic agent's multi-step reasoning capability solves a problem this narration-only task does not have. Option C's deterministic compute-then-weave shape does the same job with no tool-selection overhead.

**Carried risk into Solution, independent of the A vs. C choice:** Option C's per-employee pre-computed half runs at the same full-employee-universe nightly batch scale as Option A — System Sizing's 130,000-employee platform assumption (~47,767 actual via `employees_search_index`), two to three orders of magnitude above Compute's existing ~600-employee daily incremental run. That existing run is deterministic feature math at 0.5ms/feature; this is an LLM call per employee, seconds not milliseconds. Nothing in Frame, Research, or this Evaluate has sized whether that batch completes inside its nightly window, what concurrency it needs, or whether it collides with provider rate limits, independent of the per-generation dollar cost OQ-4 already tracks below. This does not change the recommendation, since every pre-computing option (A and C) carries it equally and Option C still wins on narrative quality, but Solution must size it before committing to a nightly cadence.

**Falsifiability:** if Solinor's real comparison-set cache-hit telemetry (once available) shows comparisons are repeated often (contradicting the "high-cardinality, low-reuse" assumption), Option B becomes more attractive and this recommendation should be revisited.

## Open Questions for Implementation

- Real comparison-set cache-hit rate: no telemetry exists yet, genuinely unresolvable before implementation (owner: Product/analytics)
- Solinor's acceptable wait time and trigger preference (shortlist-add / comparison-open / request-only): externally blocked (owner: Solinor)
- Role-filtering enforcement point (write-time vs. read-time, or both as defense-in-depth) should be designed once for the shared Decision-5 deployment and reused across Decisions 1, 2, and 3 (owner: @architect / Access Management design)
- Total LLM cost per nightly batch vs. per-comparison-request at realistic volume: needs Solinor's cost-per-generation input (owner: Solinor)
- Nightly batch throughput and window-fit at full employee-universe scale (130,000 platform assumption; ~47,767 actual via `employees_search_index`): required concurrency, provider rate-limit exposure, and partial-failure/retry handling for a per-employee LLM call at this volume have not been sized against System Sizing's figures; Decision 4's model provider selection and Decision 5's Container App concurrency model both bear on the answer (owner: @architect, once Decision 4's provider is confirmed)

## Recommendation

**Recommended option: Option C's deployment shape, running Option A's token flow — "Option C (w/ A's flow)"**

A hybrid: **Option C's** per-mode Lambda bundles (`src/handler-none.ts` / `handler-basic.ts` / `handler-oidc.ts`, selected via a CDK context parameter at synth time) running **Option A's** token flow (direct Entra ID OIDC — authorization-code + PKCE against the Microsoft identity platform directly, no Cognito). This is the developer's explicit steer: Option A's runtime/protocol shape and Option C's deployment/build-selection shape are complementary dimensions, not competing alternatives, as Research's own analysis of Option C already noted.

From the Requirements matrix, this combination scores ✅ on EC1 — static per-mode bundles are the strongest form of "not a runtime toggle," stronger than A's single branching bundle — and ✅ on EC2, EC3, and EC4 by inheriting A's most-literal satisfaction of the no-separate-authorizer and auth-code+PKCE requirements. It also scores ✅ on "minimizes new AWS service dependencies" (no Cognito, per the developer's stated preference, Assumption #5 in `design/Report.md`) and ✅ on app-registration count under "minimizes per-instance operational footprint" (one registration, same as A alone).

From the Tradeoffs table, Security and Integration Complexity both land favorably for this combination: Security scores ✅ because C's static separation removes the dead-code-path audit burden a single branching bundle (pure A) would carry — the one place C clearly outscores A alone. Vendor Lock-in stays ✅ (low) since the underlying token flow is standards-based OAuth2/PKCE, portable beyond Entra ID.

The acceptable tradeoff is Operational Excellence, the weakest cell for this combination (❌ — triples build configs and test suites vs. one branching bundle). This is accepted as a one-time build-tooling cost rather than a recurring operational one, bought in exchange for a real security property (no `AUTH_MODE` dead branches to audit per deployment). Silent token refresh (a confirmed hard requirement, Assumption #2) must still be hand-built against the Microsoft identity platform since this stays off Cognito — accepted as the direct cost of avoiding a new AWS service dependency, consistent with the developer's stated preference.

Disqualifying/deprioritizing factors for the other options: **Option B** (Cognito) is not disqualified on viability but is deprioritized — it fails "minimizes new AWS service dependencies" (❌) against the explicit developer preference (Assumption #5), despite scoring better on Reliability and Operational Excellence via native refresh/revocation. **Option D** (external perimeter) fails outright — ❌ across EC2, EC3, and EC4 in the matrix — because it does not implement OIDC inside the existing Lambda@Edge handler at all, directly contradicting the Frame's confirmed requirement; it is the one option the matrix shows as non-viable, not merely sub-optimal. **Option E** (CloudFront Function split) scores ❌ on Operational Excellence and Integration Complexity for a benefit (reduced Lambda@Edge invocation cost/latency) the matrix and tradeoffs tie to a traffic scale (~10 internal users) this site doesn't have, so the added second-runtime complexity isn't justified here.

This recommendation is falsifiable: if the ~10-user scale assumption changes materially — this pattern reused across many more deployed instances where Cognito's native refresh/revocation would amortize better, or "minimize new AWS service dependencies" stops being a stated preference — Option B should be revisited.

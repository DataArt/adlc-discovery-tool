# ADLC-006: Agent Orchestration Framework Choice — Evaluate

_Produced by the Evaluate phase._

## Context

Decision 5 (Agent/Orchestration Runtime Hosting) recommends **Option B (new sibling Azure Container App, with a dedicated warm min-replica for the live trigger)**, driven by weighting "no cold-start risk for Ask Insights's live conversational trigger" at 1.0, the maximum weight in that matrix. Decision 6 (this file) evaluates the framework choice on its own merits, independent of which hosting substrate Decision 5 uses: the Matrix below has no "fits Decision 5's hosting" row, since coupling the two conflates two separate decisions. One fact matters as context, not as a scored row: a Container App is a long-running, persistent process, the kind of host LangGraph's `StateGraph` and `PostgresSaver` checkpointer assume works best. Container Apps itself provides no built-in state/checkpoint primitive the way Durable Functions' Task Hub did, so **no option here gets a free checkpointing mechanism from the hosting substrate** — a framework's own memory story matters on its own terms, not as a composed hosting-fit score.

Options scored (from `01 Research - Agent Orchestration Framework.md`): A — LangGraph TS, B — Plain LangChain TS, C — LlamaIndex TS, D — Vercel AI SDK, E — Hand-rolled state machine, F — Azure AI Foundry Prompt Agents, G — Azure AI Foundry Hosted Agents. F and G are cross-cutting, conditional options; see the shared cross-cutting file. Both are scored here for completeness, on the same basis used in Decisions 4 and 5, even though each resolves the framework question by replacing or hosting it rather than selecting among Options A-E on equal footing.

## Recommendation

**Recommended option: Option A — LangGraph (TypeScript).**

LangGraph's `PostgresSaver` checkpointer composes directly with Decision 5's persistent Container App process, the long-running host a checkpointer needs. Container Apps provides no hosting-level state primitive of its own, so Option E (hand-rolled) gets no free offset for its memory layer. This Decision 5 fact is narrative context only, not a scored criterion in this matrix: Decision 6 is evaluated on its own merits, independent of Decision 5's hosting substrate. Ask Insights requires cross-turn conversational memory, an explicit Frame requirement. LangGraph provides this off the shelf with a documented Postgres-backed implementation; every other option (B, D, E) must build and own that storage from scratch with no hosting-level help.

The proportionality concern against LangGraph (a bounded 3-capability router may not need a full graph framework's dynamic routing) is real, weighted at 0.7, and is outweighed by built-in memory alone, weighted at 0.75. LangGraph's remaining costs, a smaller TS community than its Python sibling and the heaviest dependency tree of the framework options, are accepted risks for a platform of this size against the alternative of building an equivalent checkpointer by hand with no framework behind it.

Vercel AI SDK (Option D) remains a reasonable fallback if LangGraph's TS maturity proves insufficient in practice (its own TS-first SDK with no Python-parity question is a genuine strength), but it does not solve the memory problem the way LangGraph does, so it is not the primary recommendation.

LlamaIndex (Option C) is dropped on proportionality grounds: its core differentiator, retrieval/indexing over vectors, is unused under this Frame's no-RAG constraint. Plain LangChain (Option B) has no checkpointer of its own; building one by hand on top of Container Apps, which provides no hosting-level state primitive, is a genuine build cost with no offset.

Foundry Prompt Agents (Option F) is excluded from direct comparison: choosing it eliminates the framework question entirely rather than selecting one, and converges Ask Insights onto something closer to Decision 3's own Option C. Foundry Hosted Agents (Option G) is excluded for a sharper reason than proportionality: it fails this decision's highest-weighted criterion outright, supporting only Python and C#, not TypeScript/Node.js, the same disqualifying stack constraint confirmed in Decisions 4 and 5. On a Python- or C#-based platform, G would be a genuinely strong contender — it is the only option in this matrix whose durable state store is explicitly documented to hold checkpoints for a bring-your-own framework such as LangGraph, and its VM-isolated per-session sandboxes give it the best Performance Efficiency score of any Foundry option. Neither F nor G is folded into this matrix's Recommendation; both are evaluated as their own cross-cutting choices.

**Falsifiability:** if Decision 5 is ever revisited back toward a Durable Functions or Synthetic-extension substrate (for example, if Option B's VNet subnet budget check comes back negative with no remediation), this recommendation should be revisited too, since LangGraph's checkpointer would once again compete with that substrate's own state model.

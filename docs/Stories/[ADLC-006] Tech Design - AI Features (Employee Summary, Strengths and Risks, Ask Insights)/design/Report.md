### WAF — Evaluate — 2026-10-12 (revised) — Decision 5: Agent/Orchestration Runtime Hosting Substrate

_Recommended option: B — New sibling Azure Container App (supersedes the Option C recommendation above)._

**Reason for revision:** re-scored with "no cold-start risk for Ask Insights's live conversational trigger" weighted at 1.0 (max), developer-directed, since cold start on a live chat feature is a user-facing reliability issue, not a minor caveat. Flex Consumption's "always ready instances" mitigation (Options C/D) does not eliminate cold start and is unproven in this codebase; Option B's dedicated warm min-replica does.

| Pillar                 | Rating | Headline                                                                                                                 |
| ---------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------ |
| Reliability            | 🟢     | Independent, isolated scaling unit; no shared-process contention with unrelated BFF requests                             |
| Security               | 🟡     | New resource class and VNet subnet budget to confirm (OQ-1 in the Evaluate file)                                         |
| Performance Efficiency | 🟢     | Dedicated warm replica eliminates the cold-start risk that drove this revision, pending load-test confirmation (OQ-2)    |
| Operational Excellence | 🟡     | New containerized CI/CD pipeline not exercised anywhere in this codebase (OQ-3)                                          |
| Cost Optimization      | 🟡     | Min-replica reintroduces an always-on cost for the live trigger; a known, bounded trade against unmitigated latency risk |

**P1 items (resolve before implementation):**

- Confirm VNet subnet budget for a new Container Apps Environment (OQ-1) — this option is not viable without it.

### WAF — Evaluate — 2026-10-12 (revised) — Decision 6: Agent Orchestration Framework Choice

_Recommended option: A — LangGraph (TypeScript) (supersedes the Option E recommendation above)._

**Reason for revision:** Decision 5 moving from Durable Functions to Container App removed the only reason LangGraph's checkpointer was disfavored (it no longer competes with a Durable Functions Task Hub state model). Container Apps also provides no hosting-level state primitive of its own, so hand-rolled memory (Option E) lost the partial offset it previously had — LangGraph's built-in `PostgresSaver` checkpointer is now a clear, not marginal, advantage for Ask Insights's required cross-turn memory.

| Pillar                 | Rating | Headline                                                                                                |
| ---------------------- | ------ | ------------------------------------------------------------------------------------------------------- |
| Reliability            | 🟢     | Checkpointer now composes cleanly with Container App hosting instead of competing with it               |
| Security               | 🟡     | LangSmith data-residency question still open (OQ-3 in the Evaluate file)                                |
| Performance Efficiency | 🟢     | No cold-start-related composition tension once hosted on a persistent Container App                     |
| Operational Excellence | 🟡     | New framework idioms to learn; no off-the-shelf debugging tooling beyond what LangGraph itself provides |
| Cost Optimization      | 🟡     | Heaviest dependency tree of the framework options, an accepted tradeoff for built-in memory             |

**P1 items (resolve before implementation):**

- None — the remaining gaps are implementation-time verifications (TS checkpointer maturity, tracing data-residency), not architecture-level blockers.

Full elaboration: `design/02 Evaluate - Agent Orchestration Framework.md`

### WAF — Evaluate — 2026-10-12 (revised) — Decision 3: Ask Insights

**Reason for revision:** Decision 6's revised recommendation (LangGraph) was driven significantly by Ask Insights's own requirement for built-in cross-turn conversational memory, which reopened Research's Option E for this decision — the original version excluded it outright on the grounds that it matched neither Decision 5 nor Decision 6. It now matches both, and is the only option that provides that memory requirement off the shelf (via `PostgresSaver`) and resolves multi-capability answer synthesis by construction (a named `synthesize` node), rather than leaving both as open design questions for a hand-rolled option to solve from scratch.

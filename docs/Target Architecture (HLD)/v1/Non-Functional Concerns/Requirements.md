# Non-Functional Requirements

| ID     | Category   | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Priority |
| ------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| NFR-1  | Security   | All site routes must be protected per the configured `AUTH_MODE` (`none`/`basic`/`oidc`); in `basic` mode, unauthenticated requests receive `401 WWW-Authenticate`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | P1       |
| NFR-2  | Security   | Credentials must not be hardcoded in source — loaded from Secrets Manager at cold-start runtime via `GetSecretValue`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | P1       |
| NFR-3  | Operations | Region is deployment configuration — never hardcoded in source or documentation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | P1       |
| NFR-4  | Operations | All infrastructure defined as code (AWS CDK) — no manual provisioning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | P1       |
| NFR-5  | Operations | VitePress build must fail on any dead internal link — `ignoreDeadLinks` must not be set in `config.ts`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | P1       |
| NFR-6  | Security   | Comments (giscus) are **off by default** (`VITE_GISCUS_ENABLED` unset) and must only be enabled when `GITHUB_REPO` is a public repository. Penetration testing (2026-10-23) confirmed giscus's API serves a repo's Discussions to any unauthenticated caller on the internet regardless of the repo's visibility, completely independent of `AUTH_MODE` — not merely "ungated for anyone who reaches the page" as previously assumed, but ungated for anyone who knows the repo name, full stop. Posting is still gated by GitHub repository permission (verified — accounts without access cannot post) once a public repo is in use. See `docs/Engineering Guide/09 Harness Security.md` and `Infrastructure/04 Giscus Setup.md`                                                                                  | P1       |
| NFR-7  | Operations | CloudFront viewer requests and S3 object reads on the site bucket must be logged to a dedicated, private logs bucket (`DocsStack`) — the only way to detect brute-forcing or credential sharing after the fact, since the Lambda@Edge auth handler itself keeps no record of who authenticated in `basic`/`none` modes; in `oidc` mode, the handler logs the authenticated principal alongside CloudFront's `x-edge-request-id` for correlation with CloudFront/S3 access logs                                                                                                                                                                                                                                                                                                                                      | P2       |
| NFR-8  | Security   | When `AUTH_MODE=oidc`: authentication uses Entra ID authorization-code + PKCE directly, with no intermediary IdP; JWT signature must be verified against cached JWKS before granting access, failing closed on an invalid or unverifiable signature; the post-login redirect target must be validated as a same-origin relative path, rejecting absolute or protocol-relative values; no session revocation mechanism exists — a compromised or offboarded session remains valid until token expiry, an accepted limit                                                                                                                                                                                                                                                                                              | P1       |
| NFR-9  | Security   | CloudFront attaches a `ResponseHeadersPolicy` to every response: `Strict-Transport-Security` (1 year, includeSubDomains, preload), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` restated as `frame-ancestors 'none'` in CSP (which browsers prioritize when both are present), `Referrer-Policy: strict-origin-when-cross-origin`, and a `Content-Security-Policy` scoped to `'self'` plus `https://giscus.app` for script/style/frame/connect/img — `'unsafe-inline'` remains on `script-src`/`style-src` for VitePress's own inline bootstrap scripts and giscus's host-page styling, an accepted gap until those move to nonces/hashes                                                                                                                                                             | P1       |
| NFR-10 | Operations | Site bucket (`SiteBucket`) retention: versioning exists for rollback of a bad deploy, not long-term backup — noncurrent versions (including content deliberately removed from the site) expire after 90 days via an S3 lifecycle rule, and resulting delete markers with no noncurrent versions behind them are removed. Current objects expire after 3 years as a backstop if the manual engagement-end cleanup below is missed — well beyond this engagement's fixed duration, so it should never fire in the ordinary case. Logs bucket (`LogsBucket`) expires access logs after 90 days. Neither bucket is emptied automatically at engagement end (`RemovalPolicy.RETAIN`) — deleting all client content when the engagement concludes is a manual step owned by the engagement lead, not an automated process | P2       |

## Constraints

- No cost ceiling defined for this engagement
- Small team, internal access only (~10 users)
- Fixed-duration engagement scope — all client content in `SiteBucket`/`LogsBucket` must be manually deleted when the engagement ends (see NFR-10)

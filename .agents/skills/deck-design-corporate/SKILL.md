# Deck Design

## Mission

You turn a deck brief into a strong first-pass artifact, **expressed as
real HTML slide files** that compose on top of the DataArt Corporate Slides
Kit (canvas 1920×1080).

The narrative is yours. The visual grammar belongs to the kit — entirely.

You do **not**:

- substitute the kit with any external framework,
- invent a parallel visual system,
- edit anything inside the kit (`shared/`, `templates/`,
  `showcase/`, `assets/`) — those are read-only kit files.

You **do**:

- read the kit (`tokens.css`, `layouts.css`, `components.css`, the ~30
  templates, the showcase) before drafting,
- pick a template per slide,
- materialise it into `decks/<your-deck>/` — at the **project root** (git root of
  the cwd, else the cwd; resolved by `scripts/resolve-output-dir.sh`, never the
  skill folder; override with `$DECK_OUTPUT_ROOT`) — with the right relative paths,
- replace `<!-- TODO: replace -->` placeholders with real content,
- adapt copy, illustration choice, accent colour, and density inside the
  kit's grammar — but when you fork a DataArt-branded as-is slide (above all
  `asis-fastfacts`) for client content, swap out the DataArt-specific assets:
  never carry DataArt's global-presence map onto a client slide. For a client
  "X today" / company overview, use `content-stats-map` with the client's
  stats and a client-relevant visual or a labelled placeholder,
- introduce new sub-objects only when the kit clearly does not cover the
  content — and only by composing existing tokens/components,
- run programmatic pixel + console verification via Claude Preview MCP
  before declaring the deck ready.

Reuse priority, in this exact order:

> **Reuse a template → Adapt the template → Compose a tiny sub-object from
> existing tokens → Escalate.**

stderr — follow them, ask the user where the kit lives, or halt.

- `kit-corporate/shared/tokens.css`
- `kit-corporate/shared/components.css`
- `kit-corporate/shared/layouts.css`

`<skill-dir>/kit-corporate/`. Slides will reference it via
`../../../kit-corporate/shared/<file>.css` paths (canonical three-level
form — the same `materialize-slide.sh` would have used).

### Failure handling

If ANY of the three reads / the bash probe fails, **halt and emit**:

- `escalation_flags: kit_unavailable: <which file or probe failed>`
- A clear message to the user:
  «Kit is unavailable in this environment. Without it I cannot
  produce a DataArt deck. Set $DECK_KIT_ROOT to point at a valid
  kit, or place the kit at a discoverable location, and re-invoke.»

**Do NOT fall through to producing a Tailwind / inline-style /
shadcn-substituted deck.** A deck without the kit is not a DataArt
deck. The skill's value is the kit's visual language; without it,
refuse the task rather than ship a fake.

proceed if this field is missing or empty.

_Why a hard gate:_ under pressure agents rationalise MUST-language away and
freelance Tailwind/inline HTML (the Part 40 Cowork audit). A probe +
escalation makes the failure uncatchable — kit found and used, or task halts
with a clear reason.

## Non-Negotiable Rules

Each rule carries a `Why:` so edge cases are judgable instead of robotically
applied.

1. **The kit is the only source of visual components and final assembly.**
   Substitute nothing.
   _Why:_ the ~30 templates already prove out brand-consistent positions,
   type scale, and component semantics; external CSS (shadcn / Tailwind /
   Bootstrap / custom) makes the deck stop feeling like DataArt.
2. **Never edit anything under `/kit-corporate/`** — `shared/`, `templates/`,
   `showcase/`, `assets/` are read-only.
   _Why:_ the kit is shared infrastructure; editing it mid-run silently
   changes every existing template and every future deck.
3. **Reuse priority is template → adapt template → compose tiny sub-object
   → escalate.** Compose, do not invent.
   _Why:_ the ~30 templates already cover the canonical layouts; reaching
   past them is almost always a misread of the template list.
4. **Canonical positions are fixed** (canvas 1920×1080): logo top-right,
   heading zone top-left with the accent rule, footer chrome along the bottom,
   content inside the 153.333 → 1766.667 side margins. **Exact pixel values
   live in `references/kit-map.md § 1`** (single source of truth) and the
   verifier enforces them.
   _Why:_ these positions are identical on every content slide; moving one
   visibly breaks brand identity even if it looks "fine" in isolation.
5. **Typography only via `.txt-*` classes; colour only via `--c-*` / `.c-*`** —
   no inline px sizes, no hex literals. The kit has no gradient tokens (the
   only gradient is `.tag.is-case-study`; vivid title backgrounds are raster).
   _Why:_ brand identity depends on a small set of named tokens; hardcoded
   values bypass them and drift the deck visually slide-to-slide.
6. **One slide does one job.** If a slide tries to do two, split it.
   _Why:_ multi-purpose slides reduce comprehension speed; presentation
   pacing is the cheapest way to make a deck feel professional.
7. **Run pixel + console verification before declaring done** — see
   `references/verification.md`.
   _Why:_ HTML can render "looks fine in the preview" while a layer is
   off by 30 px or an asset 404s; programmatic checks catch what eyes
   miss.
8. **Never materialise ≥ 6 slides without Checkpoint #0 approval** —
   see Workflow Step 5b and `agent/references/execution-checkpoints.md`.
   _Why:_ the plan-review step costs 30 seconds; rebuilding 8 slides
   when the user's mental model didn't match the agent's costs
   30 minutes of throwaway work. Small smoke decks (< 6 slides) skip
   this gate.
9. **Never export pptx without Checkpoint #1 approval** — see
   Workflow Step 10.
   _Why:_ the pptx is the irreversible deliverable handoff. HTML can
   be iterated freely while staying inside the agent's loop; pptx
   leaves the loop and lands in the client's inbox. The user-OK gate
   is the last point at which a problem is cheap to fix.
10. **Never declare the deck complete without firing Checkpoint #1.**
    Verify-pass is not "done". Step 9 → Step 10 is the only
    legitimate transition. Going from Step 9 "verification
    complete" straight to writing a final summary (e.g. "deck
    is ready", "13-slide deck is ready", "marking verification
    complete" followed by handoff text) is a process violation
    that **silently denies the user a pptx they likely wanted**.
    The user can't ask for a pptx retroactively — by the time
    they see your summary, the workflow is over.
    _Why:_ the Cowork production test on 2026-05-21 confirmed
    agents will skip Step 10 silently when SKILL.md gates are
    only weakly worded. The user explicitly opted into a
    non-skippable user-OK gate before pptx; respect it. If you
    catch yourself about to write the summary right after
    verify, that's the signal — fire Checkpoint #1 first.

## AIMS — narrowed for deck-design

The methodology lives in **`agent/references/aims-judgement.md`** —
read it once per run. It owns the deep probes, the 60/40 visibility
rule, the hypothesis-first protocol, and the ambition floor. This
section adds the deck-specific accents.

Upstream decisions (deck vs product, deck purpose, visual direction)
are made before this skill is invoked — by the user themselves in
standalone mode, or by `orchestrator.md` in the AIMS64 platform.
Inside this skill, the visual grammar is delegated to the kit, so **A
and I carry the narrative; M is mostly "pick & compose"; S is
verification + ambition defence**.

### A — Approach (story angle)

Run the Approach probes from `aims-judgement.md § A`, with deck-specific
emphasis:

- **One-sentence deck thesis.** What the deck makes the audience
  believe.
- **Audience belief baseline.** What does the audience _already_
  believe? What evidence would actually surprise them? (If your
  evidence wouldn't surprise this audience, the deck isn't doing work.)
- **The one quotable slide.** Which slide will the audience screenshot
  / quote / forward to a colleague? Design backwards from that.
- **Regret check.** What would make the stakeholder regret showing this
  deck to their team?
- **Hypotheses.** Produce 2–4 per `aims-judgement.md` template — at
  least one `bold` (a strong narrative move that risks pushback) and
  one `defensible`. Each hypothesis must specify the audience's
  expected reaction in one line.

### I — Interaction (presentation mode + narrative arc)

Run the Interaction probes from `aims-judgement.md § I`, then commit to
a **presentation mode** before drafting:

- `live_presentation` — someone walks through it. Pace controlled by
  presenter. Higher density tolerated; speaker notes meaningful.
- `leave_behind_pdf` — read alone after the meeting. Every slide must
  stand on its own; no "as I explained on slide 4" callbacks.
- `interactive_walkthrough` — web-served, paced by reader. Density
  lower; visual hierarchy more critical.
- `async_send_and_forget` — email-attached, opened cold. First viewport
  has to do all the work.

Then draft the arc (opener → context → why now → proposition → proof →
operating model → CTA). Per-slide job in one sentence. **No hard cap
on slide count** — content density wins. Honest 5-slide leave-behind
and an honest 20-slide deep-dive are both valid; pad to neither.

Mark control moments: if `live_presentation`, where does the presenter
pause for Q&A? If `leave_behind_pdf`, where can the reader skim past
without losing the thread?

### M — Modularisation (kit reuse + standardisation)

For each slide, pick the closest template per `references/kit-map.md`,
mark `reused | adapted | new-object`. Then run the Modularisation
probes from `aims-judgement.md § M`:

- **Quality bar (explicit).** `pre_sale_credibility` (must look right,
  not ship) → looser composition rule enforcement.
  `mvp_for_production` (a real deck someone will present) → strict
  composition rules. `production_grade` → strict + verification gate
  before output.
- **Slide-level reusables.** Did any sub-object you composed turn into
  something worth promoting to the kit (a new template, a new asset
  family)? Flag it in `new_objects_introduced` and surface it as a
  `reusable_candidate` in the output.
- **Iteration guardrails.** If this is iteration mode, what slides are
  locked, what's still in motion?

### S — Stewardship (verification + ambition floor)

Run the verification checklist in `references/verification.md`. Then
run the Stewardship probes from `aims-judgement.md § S`:

- **Cover-slide ambition check.** The cover is the single most visible
  trim-for-safety target. After all other slides are drafted, look at
  the cover again: is the headline punchy or passive? Did "safe"
  language creep in? If yes, re-bold before declaring done.
- **Trust risks (≥2 for client-facing).** Concrete, not generic.
  Examples: "logo wall has 2 placeholder logos still", "the audit-stat
  in slide 3 is from a 2023 study — date it visibly or pull a 2025
  one", "premium adjective 'best-in-class' in slide 5 has no proof
  attached".
- **Anti-AI-signal sweep.** Eyebrow kickers, "recommended sample"
  pills, generic feature-card grids — see
  `references/composition-rules.md § Anti-AI-signal rules`.
- **Follow-up path.** What happens after this deck ships? Sales call?
  Designer polish? Engineering review? Name it.

Stewardship manages risk; it does **not** flatten ambition.

## Workflow

1. **Read the brief** — natural-language description or handoff envelope.
   In handoff mode, validate per `references/aims64-handoff.md`. In
   standalone mode, summarise the brief in one sentence and confirm deck
   purpose, audience, and approximate length. Continue with explicit
   gap callouts if something recoverable is missing.
2. **Define thesis, audience, emotional + belief targets** internally; do
   not draft visuals yet.
3. **Read the kit** — run `scripts/kit-overview.sh`, then read
   `references/kit-map.md`. Open `kit-corporate/showcase/index.html` in the
   browser preview to ground concrete choices.
4. **Build the narrative arc & slide list — AIMS-derived.** Read
   `references/narrative-arc.md`. The arc is **not improvised** — it is
   a sequence of named slots, each backed by a specific AIMS output
   from Step 2 (`agent/references/aims-judgement.md`):

   - Cover open → required.
   - Opportunity / problem → AIMS-A hypothesis.
   - **Why us / proposition** → **always slot 3 or 4, never deep**.
   - Solution → AIMS-A direction.
   - Interaction / how it works → AIMS-I (optional).
   - Process → AIMS-M (optional).
   - Proof / case studies → AIMS-M references (optional but recommended).
   - Trust risks → AIMS-S trust_risks (optional).
   - Follow-up / next steps → AIMS-S follow_up_path; second-to-last.
   - Cover close → required, last.

   Optional slots are included **only when their AIMS source is
   non-empty**. Slot order is fixed (so the audience reads the same
   narrative shape across all DataArt decks); slot density varies
   (1 slide for «commercial model» on a small deck, 2-3 on a large
   one). **No upper cap on slide count** — honest narrative density
   wins. Plan-review (Checkpoint #0) is essential for any deck ≥ 15
   slides. Per-slide job in one sentence. Don't finalise copy yet.

   > **Migration mode skips this step.** If you are re-skinning a source deck
   > (`references/deck-migration.md`), the source's slide order/count is
   > authoritative and this fixed skeleton does NOT apply — the inserts below
   > are offered once, off by default. Steps 4's skeleton + the
   > `mandatory_slides_present` gate are for fresh builds only.

   **The AIMS arc fills the middle of a FIXED corporate skeleton —
   read `references/kit-map.md § 6` now and wrap the arc in it:**

   ```
   cover
     → asis-fastfacts        ALWAYS — right after cover
     → asis-capabilities     ALWAYS — right after fast-facts
     → …AIMS arc content + section dividers…
     → [asis-partnerships]   only if the project has partnerships/integrations
     → [asis-microsoft]      only if the project involves Microsoft
     → [content-team/-roles] ASK-first (Step 5b) — only on opt-in / team data
     → content-nextsteps     ALWAYS — the "what happens next" roadmap
     → asis-contacts         ALWAYS — second-to-last, right before final
     → final
   ```

   The four `ALWAYS` inserts (fast-facts, capabilities, next-steps,
   contacts) are **mandatory in every deck** — they are NOT AIMS-gated and
   NOT your discretion. A deck without them is incomplete (this is the
   most common real-deck failure). They go in the slide list at Step 4 and
   are re-checked at Step 9c + the pre-output preflight.

5. **Pick a starting template for each slide** — fork-from-template.
   Choose the template via `references/kit-map.md § 7 content-shape →
template chooser` (full catalog + captions in § 5) that most closely
   mirrors the content shape; each template carries
   `forkable: true` in its `<!-- recipe: -->` block (see
   `references/canvas-zones.md § 4`). Templates ARE the canonical,
   pixel-faithful examples — there is no separate reference-slide pool.
   Copy via `scripts/materialize-slide.sh`, then replace text in
   `zones_content` and preserve `zones_decoration`.

   Mark `reuse | adapt | new-object` for each slide, and list which
   `kit-corporate/assets/*` illustrations will be used.

   **Variety pass (anti-monotony).** After picking per-slide templates, scan the
   sequence as a whole: if the same content template lands on more than two
   consecutive slides, rotate the rendering on the extra ones via the
   `references/kit-map.md § 7` rotation menu — and make sure the deck draws on the
   wider palette (at least one image, and a stat slide where the content has
   numbers) rather than one grid on repeat. This is independent of backgrounds
   (Step 5a): the section keeps one background; only the layout rotates.

   Concretely, when forking by hand: copy
   `kit-corporate/templates/<name>.html` into
   `decks/<deck-name>/slide-NN-<your-slug>.html`; fix asset paths
   (`../shared/` → `../../kit-corporate/shared/`, `../assets/` →
   `../../kit-corporate/assets/`); replace text in `zones_content` only
   (preserve `zones_decoration`); update the page-number. Recipe block
   can be left as-is or removed.
   5a. **Assign backgrounds by ROLE + SECTION** (Corporate model — there is
   NO slide-to-slide variety rule; consistency within a section is the
   goal). See `references/kit-map.md § 4 Backgrounds`:
   - **Title backgrounds** (`bg-title-*`, dark) come from two fixed pools:
     `bg-title-03/04/05` (vivid) → the **cover** (default 03); the **final**
     slide uses **{03, 05} only — `bg-title-04` is FORBIDDEN on final** (default
     final = 05). `bg-title-01/02/06` (muted) → **section dividers**, one per
     section. `statement.html` keeps `bg-title-06`.
   - **Content backgrounds** (`bg-content-01…08`, light): pick **ONE per
     section** and reuse it on **every content slide in that section** — a
     section reads as a unit. Different section → different content-bg.
   - A few constructor slides (pipeline / next-steps) are plain **white**;
     the two-logo cover uses `bg-cover-light`.

   So `bg_palette` = a map of section → content-bg + the title-pool picks.
   Reusing the same `bg-content-*` across a whole section is correct and

6. **Draft copy** per slide: one headline, 1–3 lines of support copy,
   explicit emphasis spans (`<span class="hl-bold">…</span>`).

   **Markdown drafting markers are INTERNAL — never render in final
   HTML.** Strip or convert before materialization (composition-rules
   § 0.11):
   - `[weak]` → drop entirely OR rewrite as a concrete claim OR surface
     in `open_questions` / `human_refinement_needed`.
   - `~~strikethrough~~` → drop entirely. Drafting cross-out has no
     visible meaning in the kit.
   - raw `**bold word**` → `<span class="hl-bold">bold word</span>`.
   - raw `_italic word_` → `<em>italic word</em>`.

   **NO EM DASH — banned (Part 49).** Never use the em dash `—` (U+2014)
   in any slide copy: headlines, body, captions, table cells, footers.
   It reads as an AI writing tic and is visually heavy on a slide.
   Rephrase instead:
   - appositive / aside (`X — Y`) → colon `X: Y` or comma `X, Y`.
   - parenthetical (`A — note — B`) → parentheses `A (note) B` or two
     sentences.
   - range (`2019—2024`) → hyphen `2019-2024` or the word `to`.
     Ordinary hyphens in compound words (`end-to-end`, `CI/CD`,
     `joiner-mover-leaver`) are fine. `verify-slide.sh` blocks any slide
     whose rendered text still contains `—` (gate `em_dash_banned`).

   If a planning marker reaches Step 7, the materialised HTML must
   already be clean of markdown syntax (and of any em dash).
   6a. **Budget-check the copy BEFORE writing it (bash).** Over-long copy is the
   #1 cause of layout fixes (text crossing dividers, towering headings,
   mid-word breaks). Catch it now, not after rendering: collect your drafted
   strings as a JSON array of `{slide, kind, text}` (kind = a budget key:
   `heading-1line/-2line`, `cover-heading`, `divider-heading`,
   `statement-heading`, `nc-title`, `nc-body`, `cols3-title`, `cols5-title`,
   `ib-title`, `ib-text`, `compare-head/-item-head/-item-text`, `pipe-step`,
   `caption`, `ff-label`) and pipe it through
   `python3 scripts/check-copy-budget.py`. Trim anything it flags (or move to
   a wider layout / fewer columns) before Step 7. Budgets = kit-map § 7.

   **HARD RULE (Part 28): every slide HTML MUST link ALL THREE shared
   stylesheets, in this exact order, all resolving to `<kit>/shared/`:**

   ```html
   <link rel="stylesheet" href="../../kit-corporate/shared/tokens.css" />
   <link rel="stylesheet" href="../../kit-corporate/shared/layouts.css" />
   <link rel="stylesheet" href="../../kit-corporate/shared/components.css" />
   ```

   The `../` depth is **location-dependent** and `materialize-deck.sh` sets it
   for you — 2 levels for a deck at the project root `decks/<deck>/` (shown
   above), 3 for `tmp/decks/<deck>/`. The verifier keys on the `/shared/`
   segment + link order, **not** the prefix, so never hand-"correct" a working
   prefix to match a literal example. What matters: three sheets, this order,
   resolving to the kit.

   - `tokens.css` — CSS variables (`--c-*`), `.txt-*`
     typography. Without it, `var(--c-orange-400)` fails to resolve.
   - `layouts.css` — `.slide-stage`, `.slide`, `.layer`, `.bg-*`,
     full-bleed background variants. **Without it, the slide collapses to default
     block flow — page stretches to several thousand px tall, content
     stacks vertically with no positioning.** This is the failure mode
     from the Onepark deck regression.
   - `components.css` — `.col-table`, `.col`, `.col-eyebrow`,
     `.col-title`, `.disc-list.has-icons.is-*`, `.callout.is-*`,
     `.pill`, `.diamond-*`, etc. Without it, multi-column
     layouts collapse and bullet icons disappear.

   — always include all three. If you copy-pasted markup from a
   reference slide or rebuilt from scratch, double-check the `<head>`
   has all three link tags BEFORE running verify-slide.sh.

## Output

### Standalone mode (default)

Return:

1. The generated HTML slide files in `decks/<deck-name>/`.
2. The PPTX at `decks/<deck-name>/<deck-name>.pptx` (only if
   Checkpoint #1 → `Yes, export pptx`; otherwise omit).
3. A 5-line summary in chat: deck title, one-sentence thesis, slide
   count + brief arc (e.g. "cover → opportunity → solution → proof →
   CTA"), pixel-verification result (`scripts/verify-slide.sh` output),
   and any open questions / weak claims. Mention the pptx path if
   exported.

Do not emit a YAML envelope in standalone mode — the user just typed a
brief, they want slides back, not a contract document.

### Handoff mode

Emit a `deck_output` YAML envelope per the contract in
`references/aims64-handoff.md`. That file owns the full schema. New
fields introduced in this revision:

- `slide_plan` — present when Checkpoint #0 fired; an array of
  `{ idx, slug, template, purpose }`.
- `pptx_path` — string path or `null`. Populated when Checkpoint #1
  resolved to `Yes`; `null` when `Skip pptx (HTML only)`.
- `checkpoint_history` — array of every fired checkpoint with its
  decision and iteration count. Always present; empty `[]` only when no
  checkpoint was applicable (smoke deck < 6 slides AND
  Checkpoint #1 still ran — so in practice never empty for decks).

`desired_outcome` is **never present** in `deck_output` — the deck
pipeline is fixed at `html_then_pptx`. An incoming handoff envelope
with any other `desired_outcome` value triggers an escalation flag
`malformed_envelope: desired_outcome must be html_then_pptx or absent`.

### Quality Bar

A good output:

- has a clear throughline you can read from `narrative_summary`,
- maps each slide to a real template file in the kit,
- introduces ≤ 1 new sub-object per ~5 slides on average,
- passes the pixel + console verification block,
- is honest about uncertainty (`weak_claim`, `open_questions`,
  `human_refinement_needed`),
- never edited or referenced files outside `/kit-corporate/` and
  `decks/<deck>/`,
- gives a sales lead or designer something they can review or present in
  the next 30 minutes.

## Iteration Rules

If the user is refining a previous deck (standalone: explicit reference
to a previous run; handoff: `iteration_context` field present), treat
this run as refinement:

1. Preserve approved structure unless feedback changes it.
2. Preserve strong reused templates.
3. Apply feedback surgically — do not regenerate from scratch.
4. Summarise what changed (standalone: in the 5-line summary; handoff:
   in `iteration_context.what_changed`).
5. Carry forward unresolved issues.

## Escalation Rules

In standalone mode: surface issues directly to the user in the 5-line
summary. In handoff mode: emit them in `deck_output.escalation_flags`.

Raise or preserve escalation flags when:

- the brief needs a layout no template covers, even after adapt /
  combine / drop-a-column tries,
- the concept needs an interaction model the kit cannot encode in a
  static HTML slide,
- the brief carries real-data or sensitive-data requirements,
- the handoff envelope carries `client_brand_overlay` data — decks are
  always DataArt-style; emit `escalation_flag:
brand_overlay_not_applicable_to_decks` and ignore the field,
- the input includes a Figma URL but the Figma MCP integration is not
  bound — ask the user to connect it; do not fabricate from the link
  alone.

Do not hide these in polished output.

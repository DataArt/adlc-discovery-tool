## Recommendation

**Recommended option: Option B — New sibling Azure Container App.**

"No cold-start risk for Ask Insights's live conversational trigger" is weighted at 1.0, the maximum weight in this matrix: a live chat feature where a user is actively waiting on a reply cannot treat cold-start latency as a minor caveat to be mitigated later. Flex Consumption's "always ready instances" setting (Options C and D) reduces cold-start exposure but does not eliminate it, is unproven in this codebase, and degrades back to a genuine cold start once demand exceeds the always-ready pool. Option B's min-replica ≥1 configuration for the live trigger gives a dedicated, always-warm instance with no such ceiling; the pre-warm/batch side of the same Container Apps Environment can still scale to zero, so the cost advantage Options C/D claim over B holds only for the batch half, not the half that carries the latency-sensitive user-facing traffic.

Option B's cons (a new Terraform module, a new subnet, a containerized CI/CD pipeline not exercised anywhere in this codebase) are real build costs, but they are one-time infrastructure costs, not a recurring risk to the end-user experience the way an unmitigated cold start is on every conversation turn. Given Ask Insights is the feature this decision exists primarily to serve, reliability on its core interaction loop outweighs a one-time setup cost for a platform this size.

Option D (Synthetic extension) is set aside for the same cold-start reason as C, compounded by the fact that the Synthetic Layer does not exist in code yet, making it strictly worse than C on every other criterion too.

Option A (BFF module) scores well on cold-start (already warm) but fails the independent-scaling and operational-boundary criteria: coupling the agent workload's scaling to the BFF's own scaling unit is a real risk once Ask Insights carries live traffic, and Decisions 1 and 2's own Research already treats "model-calling in the BFF" as an open fork, not a settled default. Ask Insights's long-running, multi-tool-call conversational turns would run on the same single Node.js event loop that serves every other BFF API request, so a busy agent conversation directly degrades latency for unrelated, standard API traffic sharing that process — a real runtime-contention risk, not just a theoretical operational-boundary concern.

**This hosting choice resolves Decision 6's framework/hosting dependency.** A Container App is exactly the long-running, persistent-process host LangGraph's `StateGraph` and `PostgresSaver` checkpointer assume, so adopting LangGraph (Decision 6, Option A) composes cleanly with this hosting choice. Decision 6's Evaluate (`02 Evaluate - Agent Orchestration Framework.md`) reflects this.

Hosted Agents is the strongest technical fit in this matrix on nearly every other criterion (purpose-built LangGraph checkpoint support, outbound-only VNet, built-in observability, confirmed UK South/UK West availability, and a stronger cold-start story than Flex Consumption, though not as strong as B's dedicated warm replica), but one disqualifying, confirmed fact rules it out: it supports only Python and C#, not TypeScript/Node.js. For this all-TypeScript platform, that is a hard stack boundary, not a tuning tradeoff.

**Falsifiability:** if a load test on Option B shows the min-replica configuration's warm-instance latency is still insufficient for Ask Insights (e.g. due to the internal hop count within the container itself), or if the VNet subnet budget check (OQ-1 below) comes back negative with no remediation, revisit toward a hand-rolled retry/queue-based mitigation on top of Option C rather than reverting outright, since cold-start weight 1.0 does not change if Option B turns out to be infeasible for an unrelated reason.
